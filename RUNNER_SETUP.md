# Instructions for an agent: set up the Carter GitHub Actions runner

## Goal

Prepare the owner's home mini PC to run GitHub Actions jobs for `aaronlaikh/carter` as a repository-level self-hosted runner. Install only the software needed for the mini PC's detected operating system and the workflow this repository actually uses. Do not change application code or add/enable a workflow unless the owner explicitly asks.

Repository: `https://github.com/aaronlaikh/carter`

## Important security gate — do this before installation or registration

This repository is public. GitHub warns that self-hosted runners are generally unsafe for public repositories: untrusted pull-request code or workflow changes can compromise the persistent machine and potentially reach its files, network, or credentials. A self-hosted runner does not provide a clean, isolated machine for every job.

1. Inspect `.github/workflows/` and identify every event that could schedule jobs on a self-hosted runner, especially `pull_request`, `pull_request_target`, `workflow_run`, and any workflow that checks out or executes untrusted PR code.
2. If any untrusted/public-contributor workflow can run on the runner, **stop before registering or enabling it**. Explain the risk and ask the owner to choose a safer plan (for example, GitHub-hosted runners for public PRs, or a suitably restricted/private repository arrangement). Do not assume a `if:` condition alone makes executing untrusted code safe.
3. Do not expose home-network services, credentials, SSH keys, personal files, or other machines to workflow jobs. Do not put registration tokens or personal access tokens in this repository, workflow files, logs, or shell history.

## Before proceeding

- Confirm the owner has authorized changes on the mini PC and has physical or remote administrative access.
- Detect and report the OS/version, CPU architecture, available disk space, and whether Docker is already installed. Do not assume the machine is x86-64 or that it runs Ubuntu.
- If the OS/architecture is unsupported or the hardware is inadequate, stop and explain why rather than improvising an unsupported setup.
- Keep the system patched. Use a dedicated, non-administrator account for the runner where the OS supports it. Do not run workflow jobs as root/Administrator.
- Use outbound connectivity to GitHub over HTTPS; do not open inbound firewall/router ports for the runner.

## Install and register the runner

1. In GitHub, open the repository **Settings → Actions → Runners → New self-hosted runner** and select the mini PC's exact OS and architecture.
2. Follow the commands GitHub generates on that page to download and extract the runner. Do not guess or hard-code a runner version or download from unofficial mirrors; use current official GitHub instructions.
3. Configure it as a **repository-level** runner for `aaronlaikh/carter`, not an account-wide runner. Use a clear name such as `home-mini-pc` and, if useful, a custom label such as `carter`. Retain the standard `self-hosted` and OS/architecture labels.
4. The configuration step needs a short-lived registration token generated by GitHub. Have the owner generate/provide it interactively when needed. It expires after one hour. Do not save it or ask for a personal access token.
5. Configure the runner as an OS service so it starts after reboot, using the official instructions for the detected OS. Run the service under the dedicated runner account and verify that it starts and reconnects after a reboot.
6. Confirm in repository Settings → Actions → Runners that the runner is **Online**. Do not trigger a workflow until the security gate above is satisfied and the owner approves a test.

Official setup and service documentation:
- Add a self-hosted runner: https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners
- Configure it as a service: https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/configure-the-application
- Self-hosted runner security: https://docs.github.com/en/actions/reference/security/secure-use
- Runner requirements: https://docs.github.com/en/actions/reference/runners/self-hosted-runners

## Install Carter's runtime only if the approved workflow needs it

Inspect the approved workflow and `README.md` first. Do not install both Docker and a separate Python/browser stack without a reason.

- If the workflow runs Carter directly, install a supported Python version (the README says Python 3.10+), install the dependencies from `requirements.txt`, and install Playwright's Chromium browser plus the OS dependencies required by Playwright. Follow the Playwright instructions for the detected OS.
- If the workflow builds/runs the repository's Dockerfile, install Docker Engine using the official instructions for the detected OS, enable the Docker service, and verify a basic container can run. Granting the runner account Docker access can effectively grant elevated control of the host; explain this risk to the owner and get approval before adding that access. Do not use `sudo` inside workflow steps as a workaround.
- The current project Dockerfile installs Python dependencies and Playwright Chromium in the image. Verify it still matches the workflow before relying on it.
- Do not run a large live TCGplayer scan as an installation test. Use a minimal `--help` or other non-networking smoke test where practical, and follow the repository's scan-rate guidance.

## Workflow routing and verification

If the owner separately approves adding or modifying a workflow, use a runner label that matches the actual machine, for example:

```yaml
runs-on: [self-hosted, linux, x64, carter]
```

Adjust OS and architecture labels based on the detected machine and labels shown in GitHub Settings. Do not assume `linux` or `x64` in advance. Keep workflow permissions minimal, avoid secrets unless essential, and ensure the workflow does not run untrusted public PR code on this persistent host.

For an approved trusted-only test, verify that the job is picked up by the intended runner, completes, and leaves no unexpected processes or files. Report the OS/architecture, installed components and versions, runner name/labels/status, service status, test performed, and any owner actions still needed. Never include secret tokens in the report.

## Handoff

If setup is blocked by a missing OS detail, GitHub permission, registration token, security concern, or owner approval, stop and request only the specific information/approval needed. Do not bypass the blocker.
